Setup

Three arms, one machine, one interpreter

Control
reputation_topic_gpu/

Unchanged code. 384-dim paraphrase-multilingual-MiniLM-L12-v2, frozen per-brand UMAP (50k reference sample) + HDBSCAN.

768-dim
reputation_topic_gpu_768/

Only the encoder changes: 768-dim paraphrase-multilingual-mpnet-base-v2. Every threshold is left as tuned for 384-dim.

BERTopic
reputation_topic_gpu_bertopic/

Same 384-dim vectors. Discovery, candidate and recovery clustering handed to a fresh BERTopic fit per brand pool, library defaults.

  • Why a control run. The earlier GPU runs were on other hardware, and timings across machines do not compare. The control re-runs the current code here with the exact docker compose base and stream flags. It reproduces the earlier runs (429 topics against 426–427, 10/10 events), so the baseline is sound.
  • BERTopic still uses UMAP and HDBSCAN. They are its default components. What goes away is the pipeline's machinery around them: the frozen manifold reused across runs, the tuned settings (30 neighbours, min_samples 10), the epsilon merge, the Ward split of oversized clusters and drift refits. BERTopic defaults are 15 neighbours and min_samples = min_topic_size = 30, refitted on every pool, every run.
  • Embedding reuse. The BERTopic arm uses the same model on the same text as the control, so it reads the control's cached vectors. Its timings exclude embedding; add the control's embedding time for a cold-run figure.
  • Coherence yardstick. C_v and C_npmi are the same implementation as every earlier review (c-TF-IDF top-10 terms, ε-smoothed), scored against one fixed corpus per phase: the raw 200k CSV for base runs, the six raw stream chunks for the stream. No arm's own segmentation can move it.
  • Noise floor. Two runs of the same code on the same input differed by 0.014 in published-set C_npmi (the local vs cloud comparison of 29 Sep). Treat gaps smaller than that as a tie.
768-dim, so far
Slightly better topics at about 3.3× the cost

Fewer, larger topics and clearly better event grouping. Coherence gains are within noise. Embedding is 3.7× slower on CPU and peak RAM is 1.7× higher.

BERTopic, both phases
Not a drop-in replacement at library defaults

Fragments topics until the 600 cap binds, loses 0.04 published C_npmi, and in the stream needs twice the compute outside embedding while ID retention falls to 0.82.

768-dim embeddings at 200k

The wider encoder makes coarser, cleaner topics and groups events better. It costs 3.7× the embedding time and has not moved coherence past noise. Its adjusted mutual information against the control is 0.74, so this is a genuinely different topic set rather than a relabelling.

Past embedding, the 768 run costs the same: UMAP compresses both spaces to 5 dimensions before HDBSCAN sees them. Fewer topics make LLM labelling 11% cheaper. On the GPU deployment embedding is a smaller share (154 s of 482 s for MiniLM on the 28 Sep run), so if the 3.7× ratio holds on GPU the 768 base run would take roughly 900 s rather than 480 s. That figure is a projection, not a measurement.

What to do with this.
  • Don't adopt on this run alone. The coherence gain is inside noise; the event-grouping gain is real but modest outside Black Friday.
  • Retune --min-similarity, --duplicate-similarity and --label-merge-similarity in the 768 space first. The 0.50 floor clearly means something different here (unassigned −4.7 pp, inflation +0.09).
  • The 768-dim stream, which runs next, is the stronger test: whether the coarser topics hold their IDs and coherence across six batches.

BERTopic at 200k

What to do with this.
  • At library defaults BERTopic is not a replacement. The quality loss is outside noise and the extra topics cost 37% more LLM spend.
  • If you want to push BERTopic further, move it toward the tuned configuration: --bertopic-neighbors 30 and --bertopic-min-samples 10 (both flags exist in the copy), or a larger min_topic_size. That tests BERTopic as a framework rather than its defaults.
  • Unpinning random_state would let UMAP use all cores, at the cost of reproducibility.

Event recall ends higher and inflation stays lower, but published-set coherence trails the control in every batch.

What to do with this.
  • The frozen per-brand manifold is what makes the stream cheap and stable. The control loads its manifold in 16 s and clusters in 18–40 s a batch; BERTopic refits and clusters in 81–142 s. Matching new topics against one fixed geometry is also what holds retention near 0.99.
  • BERTopic's refit every batch shows up as churn. Each batch it mints 10–14 new IDs, forces 60–110 capacity merges and relabels a third of the surviving topics. Dashboards would see topics appear, merge and rename.
  • Its lower inflation and better final-batch event grouping are worth chasing inside the current pipeline, not by switching frameworks. Both come from tighter centroids, which the --secondary-margin and split settings already control.
